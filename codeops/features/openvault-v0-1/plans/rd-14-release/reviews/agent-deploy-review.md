# Agent Isolation, mTLS, Deployment, and Operations Review

> **Resolution**: see [00-resolution.md](00-resolution.md). The counts below are the findings at review time; all High findings are fixed.


**Scope:** Agent runtime and tests (`apps/agent/src`, `apps/agent/tests`); agent join, renewal, revocation, and listener code (`apps/server/src/agent`, `apps/server/src/security/ca.ts`, `apps/server/src/security/x509.ts`); operations and bootstrap (`apps/server/src/ops`, `apps/server/src/init`); startup and configuration (`apps/server/src/main.ts`, `apps/server/src/config/loader.ts`); deployment (`deploy/compose`, `deploy/docker`, `deploy/postgres`, `deploy/systemd`, `scripts/check-compose.mjs`); and the related integration tests. No application code was modified.

**Reviewer role:** Independent correctness and concurrency reviewer (agent isolation, mTLS, certificate lifecycle, deployment hardening, database roles, backup/restore concurrency, startup migration ordering).

**Date:** 2026-11-06

**Reviewed tree:** branch `feat/rd-13-rd-14-operations-release`, HEAD `cae3197`, plus the uncommitted RD-13/RD-14 working tree. Source and tests were inspected directly. A local Node probe was used to confirm the `X509Certificate.checkIssued` behavior cited in ADR-02; no live integration suite was run for this report.

## Findings

| ID | Severity | Finding | Evidence | Recommendation |
|---|---|---|---|---|
| ADR-01 | High | A server configured with only `OPENVAULT_DB_URL_FILE` cannot run startup migrations. `loadConfig` materializes file-backed URLs into a local copy of the environment, not `process.env`. `runStartupMigrations` only exports a URL when `migrationDatabaseUrl` is set; otherwise it calls the migration runner with no `OPENVAULT_DB_URL` in the process environment. The Compose stack masks this because it always sets `OPENVAULT_MIGRATION_DB_URL_FILE`, but the documented "migration URL defaults to the runtime URL" configuration fails at boot. | `apps/server/src/main.ts:24-39,47`; `apps/server/src/config/loader.ts:176-198`; `apps/server/blendsdk.migrations.ts:10-14`; `docs/reference/configuration.md:15-17,80-81` | When no migration URL is supplied, pass `config.databaseUrl` explicitly to the migration run (temporary environment or a runner option); add a startup integration test that uses only `OPENVAULT_DB_URL_FILE`. |
| ADR-02 | Medium | Server TLS material is not checked against the configured internal CA by signature. `ensureServerCertificate` uses Node `X509Certificate.checkIssued`, which checks issuer/key-identifier relationships but not the signature. A local probe with two CAs sharing `CN=OpenVault Internal CA` returned `checkIssued === true` for a leaf signed by the other CA, while `verify` returned false. `TlsMaterial.load` and `checkReady` also never verify the leaf signature, so a stale or replaced server pair is accepted. The `subjectAltName` checks are substring matches, so `DNS:openvaultd.evil` satisfies `openvaultd`. The Compose healthcheck disables certificate verification, so startup/readiness can look healthy while Caddy and agents reject the leaf. This contradicts `docs/guide/backup-restore.md:81-83` ("The server fails closed"). | `apps/server/src/init/tls.ts:147-176`; `apps/server/src/transport/tls.ts:78-103,128-139`; `deploy/compose/compose.yaml:164-166`; `docs/guide/backup-restore.md:81-83` | Verify `certificate.verify(ca.publicKey)`, check issuer and exact parsed SANs, and regenerate the pair on mismatch. Use a CA-verifying health probe rather than `wget --no-check-certificate`. This extends existing AC-12 with the `checkIssued` false-positive case. |
| ADR-03 | Medium | The runtime database role receives `SELECT, INSERT, UPDATE, DELETE` on every table; only `DELETE` on `audit_events` and `audit_checkpoints` is revoked. `openvault_app` can therefore delete or update `ca_keys`, `audit_keys`, and `signing_keys`, and can update `principals.status` or `workload_certs.revoked_at` to re-enable a revoked identity/certificate. The role test itself inserts an `audit_keys` row as the app role, confirming the grant. `runInit` also performs CA, administrator, and signing-key writes through the application URL even when a separate migrator URL is supplied, which forces the broad grant set. | `deploy/postgres/grants.sql:11-16`; `deploy/postgres/roles.sql:56-61`; `apps/server/tests/integration/roles.spec.test.ts:216-220`; `apps/server/src/init/index.ts:504-519,570-613`; `apps/server/src/init/ca.ts:76-91` | Grant only the DML each runtime path needs. Revoke `UPDATE`/`DELETE` on `ca_keys`, `audit_keys`, and `signing_keys`; protect `principals.status` and `workload_certs.revoked_at` through a narrower function or role. Move `ov init` bootstrap writes to the owner/migrator connection and add negative tests for deleting key rows and un-revoking a certificate. |
| ADR-04 | Medium | Database credentials are placed in process arguments during one-shot role setup. `openvault-roles` invokes `psql` with the full migrator URL in `argv`, and `init-roles.sh` passes all four role passwords through `psql -v` arguments. The values are visible in `/proc/<pid>/cmdline`, process accounting, container inspection, and possibly psql error/log context. | `deploy/compose/compose.yaml:100-105`; `deploy/postgres/init-roles.sh:22-29`; `deploy/postgres/roles.sql:44-47` | Use a `.pgpass`/`PGPASSFILE` secret or `PGPASSWORD` from a Docker secret for the connection, and feed SQL variables through stdin or a temporary file rather than `psql -v` argv. Remove the generated temp file in all paths. |
| ADR-05 | Medium | The documented systemd backup installation cannot write to its own target. The README creates `/var/backups/openvault` as root-owned `0755` and `/etc/openvault/backup.env` as root-owned `0600`, but both units run as `User=openvault`. `writePrivateFileAtomic` requires the output directory owner to equal the current uid, and the CLI cannot read the root-owned URL/passphrase files. Backup and checkpoint units therefore fail instead of producing evidence. | `deploy/systemd/README.md:9-14,20-29`; `deploy/systemd/openvault-backup.service:9-20`; `deploy/systemd/openvault-checkpoint.service:9-19`; `apps/server/src/ops/files.ts:36-64` | Create the backup directory with `install -d -m 0700 -o openvault -g openvault`; chown the URL and passphrase files to `openvault` with `0600`; add an install verification command or test. |
| ADR-06 | Medium | The reference proxy serves only `https://localhost`, while the documented start sequence sets `OPENVAULT_BASE_URL=https://vault.example.com`. `openvault-init` includes the configured host in the server certificate SAN, but Caddy has no site block or certificate for that host, so the documented deployment fails TLS/HTTP at the proxy. | `deploy/compose/Caddyfile:13-14`; `docs/guide/docker-compose.md:19-23`; `deploy/compose/README.md:19-23`; `apps/server/src/init/tls.ts:121-137` | Render the Caddy site address from the configured base URL (or document and check the required Caddyfile edit). Add a `check:compose` assertion that the proxy site host matches the configured base URL. |
| ADR-07 | Medium | A join whose response is lost after the server commits strands the agent. The agent generates its private key and CSR in memory, sends the one-time token, and only persists the identity after receiving the response. The server claims the token and signs the certificate in one transaction, but keeps no join replay entry. A retry of the same token then receives `join_token_used`; the agent cannot recover without an operator issuing a new token. Renewal has a five-minute replay cache, join does not. | `apps/agent/src/join.ts:144-174`; `apps/server/src/agent/agent-join-service.ts:155-167,242-248`; `apps/server/src/agent/agent-token-service.ts:243-257`; `docs/guide/agent.md:86-91` | Persist pending join key/CSR before the request and add a bounded join replay keyed by token hash and CSR public-key hash, or make the same token+CSR idempotent inside a short window. Add a lost-response test at the join boundary. |
| ADR-08 | Medium | The generated host secret path is keyed by Compose project and service only, not by the OpenVault project. The renderer test claims "per-project" paths but only varies the service within one project. If a Compose project/service is reused for another OpenVault project (tenant migration, restore, or manual redeploy), the new agent finds the old state/output directory. It fails closed only after an authenticated request; until the terminal cleanup, the reused bind mount still contains the previous project's delivered files, and a live or reused application container that mounts that path can read them. | `apps/server/src/scaffold/compose.ts:33-39,60-70`; `apps/server/tests/scaffold-renderer.impl.test.ts:14-23`; `docs/security/evidence-matrix.json:448-460` | Include the OpenVault project name or a stable hash in the host output and state paths, or persist the project in the agent identity and refuse/remove state whose project does not match. Add a test that renders two different projects with the same service name and asserts distinct paths. |
| ADR-09 | Low | `check-compose.mjs` does not enforce several hardening properties it is expected to protect. The root-user check accepts `0:10001` (UID 0), `cap_add` is not allowlisted, published ports are checked only for the known required service names, and image digests are required only for `proxy` and `postgres`, so a new service with a host port, `SYS_ADMIN`, or a mutable first-party tag passes. | `scripts/check-compose.mjs:72-77`; `scripts/check-compose.mjs:80-83`; `scripts/check-compose.mjs:126-131` | Parse the user field and reject UID 0; allowlist `cap_add` (only `NET_BIND_SERVICE`); inspect every service for published ports; require digests for all services in release mode. Add negative self-tests for each case. |
| ADR-10 | Low | Restore has no database or maintenance lock. The target-emptiness check runs before staging/migration, and `restoreDatabase` repeats it before `BEGIN`, not under an exclusive lock. Two concurrent restores can both pass and overwrite each other; a live server can write after the check and have its rows silently truncated. The guide requires stopping the server, but the code does not enforce it. | `apps/server/src/ops/restore.ts:482-494,520-536`; `apps/server/src/ops/database-dump.ts:316-327,336` | Take a PostgreSQL advisory lock on the target database and recheck emptiness under it. Optionally refuse when application connections exist. Document the required maintenance window in the command output. |
| ADR-11 | Low | The backup systemd unit treats the optional off-box target as mandatory for success. With `OPENVAULT_OFFBOX_TARGET` unset, `test -n "$OPENVAULT_OFFBOX_TARGET" && rsync ...` returns 1 and systemd marks a successful backup/checkpoint run as failed. | `deploy/systemd/openvault-backup.service:14`; `deploy/systemd/openvault-checkpoint.service:13`; `deploy/systemd/README.md:25-26` | Use `if [ -n "$OPENVAULT_OFFBOX_TARGET" ]; then rsync ...; fi` or prefix the command with `-` so an absent optional destination does not fail the unit. |

## Verdict

One High finding (ADR-01) is release-blocking under the repository's review-gate policy until fixed or explicitly accepted with a compensating control. No Critical finding was identified. The TLS trust-anchor issue (ADR-02) is counted as Medium because it primarily causes a documented availability/fail-closed failure; it is still a release gate item.

## Residual accepted risks and overlaps

- `SEC-03` in `crypto-auth-security.md` already records the runtime migrator URL in `openvaultd`; it is not re-counted here. `AC-01` (broad default proxy CIDR) and `AC-13` (no CA rotation path) remain open in the design challenge. ADR-02 extends `AC-12` rather than replacing it.
- Restore and KEK rotation require a maintenance window; the server can write after a rotation count check, and restore commits before post-commit verification (limitations 49 and 55). ADR-10 adds the missing restore lock but does not change the accepted ordering.
- Process-local authentication/renewal caches, single-instance operation, and the lack of shared HA state are accepted for v0.1 (limitations 16, 25, 42). Node cannot reliably zeroize strings or heap copies, and host root can read the keyring, tmpfs, and process memory (limitations 1-4).
